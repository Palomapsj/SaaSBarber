# ADR-003: Transformar o front-end em PWA

**Status:** Proposed
**Data:** 2026-11-06
**Responsáveis pela decisão:** Paloma (produto/arquitetura), time de dev front-end

## Contexto
O front-end (Next.js App Router, React, Tailwind) atende três perfis: Cliente (público, sem conta, agenda por link), Barbeiro e Admin (painel de uso diário). Queremos que o produto possa ser instalado na tela inicial do celular, com cara de app.

Forças em jogo:
- O produto é multi-tenant: cada barbearia tem nome, identidade e URL pública (slug) próprios.
- O cliente agenda uma vez, normalmente por um link (por exemplo, o link da bio do Instagram). Barbeiro e admin usam todos os dias.
- A disponibilidade de horários muda o tempo todo. Dado velho gera conflito de marcação.
- No iPhone não existe aviso automático de instalação, e notificação push só funciona com o app instalado.
- As confirmações e lembretes do produto já estão planejados por WhatsApp, e-mail ou SMS.
- O Next.js tem suporte nativo a manifest e documenta o PWA sem exigir biblioteca. Para cache offline com service worker, a documentação cita o Serwist.

## Decisão
Adotar a **Opção A**: PWA instalável, com `app/manifest.ts` e ícones, **sem service worker** por enquanto. Evoluir para a Opção B só quando houver necessidade real de push ou de tela offline.

## Opções consideradas

### Opção A: `app/manifest.ts` + ícones, sem service worker (escolhida)
| Dimensão | Avaliação |
|---|---|
| Complexidade | Baixa |
| Custo | Baixo |
| Escalabilidade | Não afeta o back-end |
| Familiaridade do time | Alta (recurso nativo do Next.js) |

**Prós:** instalável, abre em tela cheia, sem risco de dado velho, sem dependência nova.
**Contras:** sem modo offline e sem push.

### Opção B: A + Serwist, cache só de arquivos estáticos e página "sem conexão"
| Dimensão | Avaliação |
|---|---|
| Complexidade | Média |
| Custo | Médio |
| Escalabilidade | Não afeta o back-end |
| Familiaridade do time | Média |

**Prós:** carregamento mais rápido, aviso claro quando estiver sem internet, base para push de barbeiro e admin.
**Contras:** exige estratégia de atualização do service worker; versões antigas podem ficar presas em aparelhos.

### Opção C: plugin completo de cache (`@ducanh2912/next-pwa`)
| Dimensão | Avaliação |
|---|---|
| Complexidade | Média/alta |
| Custo | Médio |
| Escalabilidade | Não afeta o back-end |
| Familiaridade do time | Baixa |

**Prós:** cache amplo e automático.
**Contras:** risco de mostrar agenda e disponibilidade desatualizadas; pacote que, pelo que se sabe, teve o trabalho migrado para o Serwist (confirmar no npm); plugins baseados em webpack podem exigir configuração extra nas versões atuais do Next.js.

## Análise de trade-offs
A Opção A entrega o ganho principal (app na tela inicial) sem criar o maior risco do produto, que é dado de agenda velho. O service worker só se justifica quando houver push para barbeiro e admin ou uma tela offline, e nesse momento a Opção B resolve. A Opção C troca controle por conveniência, o que não compensa num sistema de agendamento.

## Consequências
**Fica mais fácil:** instalar o app, divulgar o link e atualizar o sistema (a atualização é imediata, sem loja).
**Fica mais difícil:** nada relevante agora. Se virmos para a B, será preciso desenhar a atualização do service worker.
**A revisitar:**
- Manifest por barbearia (nome, ícone e cor próprios, via slug) ou PWA restrito ao painel. Um manifest fixo "Barbearia Nova Era" não serve a um SaaS multi-tenant.
- Push para barbeiro e admin (novo agendamento, cancelamento). Exige chaves VAPID e guardar as inscrições no banco.
- Dados de agenda e disponibilidade nunca vão para cache. Cache de dados autenticados em aparelho compartilhado é risco de privacidade.

## Itens de ação
1. [ ] Criar `app/manifest.ts` e os ícones 192 e 512 (PNG), mais uma versão "maskable".
2. [ ] Definir se o manifest é por barbearia ou só do painel.
3. [ ] Configurar a cor da barra do navegador por tema (claro e escuro) via `themeColor` do `viewport`, já que o manifest aceita uma cor só.
4. [ ] Mostrar instrução de instalação para iPhone ("Compartilhar" e depois "Adicionar à Tela de Início").
5. [ ] Testar no celular pelo deploy do Vercel (HTTPS).
6. [ ] Reavaliar a Opção B quando push ou tela offline entrarem no escopo.
